# worker CLI 與驗證工具

## 現有 worker CLI

| 指令 | 行為與限制 |
| --- | --- |
| `python -m worker.cli init-db` | 建立／升級指定 DB；先確認路徑、backup 與授權。 |
| `python -m worker.cli collect --date YYYY-MM-DD --months-back 0` | 官方來源收集；`months-back` 只接受 0、1、2、3。 |
| `python -m worker.cli themes sync [--file PATH]` | 驗證[題材表](../INDUSTRY_CLASSIFICATION.md#7-題材表)（預設 `backend/data/themes/themes_v1.json`）並寫入 `theme_groups`／`group_memberships`；不發網路，重跑冪等。任何錯誤都整批不寫入、印出位置並 exit 1。題材榜在下一次 analyze／daily 計分。 |
| `python -m worker.cli theme-suggestions` | 由 `news_llm_results` 的題材候選重算[新聞題材建議](../spec/theme_suggestions.md)，寫 `theme_suggestions`／`theme_suggestion_news`；不呼叫 LLM、不發網路、不寫族群或題材表，重跑冪等（內容不變不改寫）。回傳來源判讀數、建議數、新題材數、與既有族群同名數及新增／更新／刪除數。不會跑 `init-db`，表不存在時回 `theme_suggestions_table_missing_run_init_db` 並 exit 1。正式 DB 唯讀副本（2026-10-18：163 則判讀、93 個建議）重算約 0.1 秒。 |
| `python -m worker.cli industry repair [--apply] [--rescore-days N]` | 依已保存的公司基本資料 raw，把錯配的一般產業 membership 搬到 canonical 群組（規則見 [INDUSTRY_CLASSIFICATION §5.1](../INDUSTRY_CLASSIFICATION.md#51-既有錯配-membership-修復)）；不發網路。預設 dry-run 只印預計變更；`--apply` 寫入並記一筆 `run_type=industry_repair` 的 ingestion run，重跑回 `no_change`。`--rescore-days N` 需搭配 `--apply`，寫入後重算最近 N 個 TAIEX 交易日的族群分數（同 analyze 的 `hot_group_v1`），並清掉這些日期停用群組留下的 rank；舊版本寫的分數列在改寫前先封存到 `group_daily_score_archive`（[hot_group_v1](../spec/hot_group.md)）；不重算訊號與 `daily_candidates`。寫入與重算在同一個 transaction，正式 DB 執行前要先停用 `daily` 與 `news` 排程（[排程](SCHEDULING.md)），完成後再恢復。證據不一致時整批不寫入並 exit 1。 |
| `python -m worker.cli instruments repair [--apply] [--include-delisted] [--max-status-share X] [--rescore-days N]` | 補回 #212 以前 collector 丟掉的資料（#393 起含 ETF 清單已不列的 ETF 行情列），只讀已存的 raw，不發網路。依序做三件事：(1) 用已存最新一次的官方清單與行情表（TWSE `t187ap03_L`、`t187ap47_L`、`company/newlisting`，TPEx `mopsfin_t187ap03_O`、`etfFilter`）做[標的狀態同步](../DATA_SOURCES.md#標的狀態同步)；(2) 加 `--include-delisted` 時，為已存行情有、DB 沒有、清單也不再列的普通股與 ETF 代號建標的（ETF 代號建成 `etf`）：另一交易所列著就標 `transferred`，否則標 `delisted`；行情停止不到 5 個交易日的不建，只列在 `unmatched`；(3) 以已存的 `dailyQuotes`／`tpex_mainboard_daily_close_quotes`／`MI_INDEX`／`STOCK_DAY_ALL` 補缺的日線，並對補到日線的標的以 `T86`／`MI_MARGN`／`insti/dailyTrade`／`margin/balance`（上櫃當日也可能是 OpenAPI `tpex_3insti_daily_trading`／`tpex_mainboard_margin_balance`，#579）補缺的籌碼。只補 DB 沒有的列、不改既有值；raw 與 SHA-256 不符時整批不寫並 exit 1。預設 dry-run 只印預計變更；`--apply` 在同一個 transaction 寫入並記一筆 `run_type=instrument_repair` 的 ingestion run，重跑回 `no_change`。`--rescore-days N` 同 `industry repair`。`--max-status-share` 預設 0.05，見 [排程看門狗](WATCHDOG.md) 的處置。正式 DB 執行前先停用 `daily` 與 `news` 排程，完成後恢復，之後跑 `indicators --rebuild`。正式 DB 唯讀副本（2026-10-24，最新交易日 2026-10-22）實測：dry-run 約 10 分鐘；`--apply --rescore-days 1` 約 11 分鐘，改 62 檔狀態（27 `delisted`、2 `transferred`、33 `dormant`）、建 15 檔標的、寫入 4,362 根日線與 4,166 筆籌碼；重跑約 5 分鐘，回 `no_change`。 |
| `python -m worker.cli instruments backfill-unmatched [--apply]` | collect 每次都會做的[標的晚建立時補寫日線](SCHEDULING.md#重跑與回補)（#388），單獨執行：只讀已存的 raw，不發網路。預設 dry-run 印出預計寫入的日期與 raw id（`written`）、補不到的列（`pending`）與一併補寫的籌碼列（`chips_written`，#415），不寫 DB；`--apply` 寫入，重跑回 `no_change`。之後跑 `indicators` 重寫受影響標的的指標。正式 DB 唯讀副本（2026-11-01，最新交易日 2026-10-30）實測：dry-run 約 1 秒；`--apply` 寫入 TWSE 7710、TPEx 6938 的 2026-10-27 日線，`indicators` 約 23 秒、重寫 2 檔共 8 列。 |
| `python -m worker.cli chips revise --start-date YYYY-MM-DD [--end-date YYYY-MM-DD] [--apply]` | 把 [#387](https://github.com/YiCheng0608/stock-lab/issues/387) 以前留在 18:30 初值的三大法人更正成較晚 capture 的值。讀已存的 T86 與 `insti/dailyTrade`、`tpex_3insti_daily_trading` raw（`data_as_of` 在起訖內，`--end-date` 預設同起日），依擷取時間由早到晚重放，套用 [重跑與回補的冪等](SCHEDULING.md#重跑與回補)的三大法人規則；不發網路，只改既有籌碼列（不新增），不改融資與日線。預設 dry-run，只印預計更正的列（`value_revision_rows`）；`--apply` 寫入並記一筆 `run_type=chip_revision` 的 ingestion run，metadata 有每列的舊值、新值與兩個 raw id。raw 檔與 SHA-256 不符時整批不寫，exit 1；raw 檔不存在或讀不出時跳過該 capture、列在 `unreadable_captures`，status 為 `partial`，exit 2。重跑回 `revised_rows: 0`；較早的 capture 與已更正的值不同，所以 `value_conflicts` 不是 0。不重算下游：已算好的族群分數、訊號證據與候選維持原值，之後的 analyze 與 candidates 讀更正後的值；候選對已有 `candidate_runs` 的日期不會重算。正式 DB 唯讀副本（2026-11-01，資料到 2026-10-30）實測：dry-run 與 `--apply` 各約 15 秒，2026-10-19～10-30 共 32 個 capture、更正 216 列。 |
| `python -m worker.cli margin-lists [--start YYYY-MM-DD] [--end YYYY-MM-DD]` | 從已存的官方融資融券餘額 raw 回補[融資標的清單](../DATA_SOURCES.md#融資標的清單) `margin_lists`（[#392](https://github.com/YiCheng0608/stock-lab/issues/392)）。不發網路；每個交易所每日取最新一份回報日期相符、有個股列的 capture，內容沒變不改寫，每日 commit 一次；未指定日期為全部已存的融資 raw。印出 `dates`、`written`／`unchanged`／`missing`／`suspicious_drop` 與兩者的 samples；全部有清單 exit 0；有日子沒有可用 capture，或清單比前一個少超過 5%（不寫）為 `partial`（exit 2）；raw 檔讀不到、不是 JSON 或與 SHA-256 不符時停在該日，status `failed` 並帶 `failed_date`（exit 1）。daily 的 collect 會寫當日，不必每天跑。需要 0022；發佈 DB 升到 0022 後跑一次。正式 DB 唯讀副本（2026-11-01，資料 2024-09-30～2026-10-30）實測：504 個交易日、1,008 份清單全部寫入，約 32 秒，`missing` 0。 |
| `python -m worker.cli no-trade-days [--start YYYY-MM-DD] [--end YYYY-MM-DD]` | 從已存的官方每日行情 raw（上市 `MI_INDEX`、上櫃 `dailyQuotes` 或當日 OpenAPI `tpex_mainboard_daily_close_quotes`）回補[官方無成交日](../DATA_SOURCES.md#官方無成交日) `no_trade_days`（[#454](https://github.com/YiCheng0608/stock-lab/issues/454)）。不發網路；每個交易所每日取最新一份回報日期相符、有表格列的 capture，以它重建該日的列，內容沒變不改寫，每日 commit 一次；未指定日期為全部已存的行情 raw。印出 `dates`、`written`／`unchanged`／`no_data`（休市日的空回應）／`missing`、`rows`、`unmatched`（找不到標的的股票或 ETF 代號）與 samples；沒有 `missing` 時 exit 0；有日子沒有任何可用 capture 為 `partial`（exit 2）；raw 檔讀不到、不是 JSON 或與 SHA-256 不符時停在該日，status `failed` 並帶 `failed_date`（exit 1）。daily 的 collect 會寫當日，不必每天跑。需要 0025；發佈 DB 升到 0025 後跑一次。 |
| `python -m worker.cli trading-halts --start YYYY-MM-DD [--end YYYY-MM-DD]` | 抓 TWSE `TWTAUU`、TPEx `revivt`，存入[減資停止買賣](../DATA_SOURCES.md#減資停止買賣) `trading_halts`（[#582](https://github.com/YiCheng0608/stock-lab/issues/582)）。`--start`／`--end` 是恢復買賣日的區間，未指定 `--end` 為今天後 60 天；每個交易所 1 個請求（經官方主機限流），寫一筆 `trading_halts` ingestion run。同一來源、恢復日在區間內的已存列以回應重建（不再列出的刪除，內容沒變不改寫）。印出各交易所的 `inserted`／`updated`／`unchanged`／`removed`／`outside_universe`／`rejected`／`conflicts`、`records` 與 `warnings`；全部成功 exit 0，有 warning 或一個交易所失敗為 `partial`（exit 2），兩個都失敗為 `failed`（exit 1）。daily 的 collect 會抓收集日前 10 天到後 60 天恢復的列，不必每天跑。需要 0030；發佈 DB 升到 0030 後跑一次 `--start 2024-09-01`。 |
| `python -m worker.cli chips provenance [--apply]` | 補寫 0021 以前籌碼列的[法人與融資各自來源](../DATA_SOURCES.md#籌碼來源)（[#395](https://github.com/YiCheng0608/stock-lab/issues/395)）。只讀來源欄缺漏或缺 raw 參照的列，不發網路、不改任何值：法人組沿用列層級的來源與 raw（#387 已讓它指向最新的法人 capture），並核對 raw 裡該代號的值與列相同，對不上的列計入 `institutional_mismatch`、列在 `institutional_mismatch_samples`，status `partial`；融資組取寫入那組值的已存融資 raw：collect run 的 `value_fill_groups` 記過該列補融資的，取那個 run 的融資 capture，否則取該交易所當日最早的融資 capture，兩者都要 raw 裡該代號的值與列相同。找不到相符 capture 的列不補（不猜來源），列在 `unmatched_samples`，status `partial`。各組的收集時間依[籌碼來源](../DATA_SOURCES.md#籌碼來源)的定義，回填只會讓列層級 `collected_at` 不變或變晚。預設 dry-run 只印統計（`sources_before`／`sources_after`、`margin_fill_run`／`margin_earliest_equal`／`margin_unmatched`、`institutional_mismatch`、`pending_after`）；`--apply` 每個交易日 commit 一次，最後記一筆 `run_type=chip_provenance` 的 ingestion run。raw 檔與 SHA-256 不符時停在該日、該日不寫（之前的日期已寫入），status `failed`、exit 1；`partial` 為 exit 2，`success` 為 0。重跑只讀仍缺來源的列，全部補完後 `dates: 0`。發佈 DB 升到 0021 後跑一次 `--apply`。不會跑 `init-db`，DB 不到 0021 時拋錯，先跑 `init-db`。正式 DB 唯讀副本（2026-11-01，資料 2024-09-30～2026-10-30）實測：504 個交易日、1,097,500 列全部補上，dry-run 與 `--apply` 各約 4～6 分鐘；17,086 列（上市 10,305、上櫃 6,781，即 2026-10-19 起 21:30 補融資的列）依 `value_fill_groups` 取 21:30 的融資 capture，其餘依當日最早相符的 capture，`margin_unmatched`、`institutional_mismatch` 都是 0；列層級 `collected_at` 只有這 17,086 列變晚（約 3～24 小時，即融資 capture 的擷取時間），其餘不變。 |
| `python -m worker.cli daily --date YYYY-MM-DD --months-back 0 [--trigger manual\|scheduler\|simulation] [--force] [--catchup-sessions N]` | 順序 catchup → collect → trading_calendar → analyze → evaluate → candidates → indicators → theme_suggestions → plan_tracking → strategy_levels → candidate_notes。catchup 先補抓目標日前最近 N 個（預設 5）缺 collect 的官方交易日（[重跑與回補](SCHEDULING.md#重跑與回補)），結果不擋目標日；`--catchup-sessions 0` 不補。collect 成功後先跑 trading_calendar（更新[官方休市表](../DATA_SOURCES.md#交易日曆)，結果不影響 run 狀態，analyze 不依賴它，[日誌與 run 記錄](SCHEDULING.md#日誌與-run-記錄)），再 analyze；analyze 成功才 evaluate、candidates 與 strategy_levels（evaluate 失敗不擋 candidates；strategy_levels 是條件價位，結果不影響 run 狀態，[日誌與 run 記錄](SCHEDULING.md#日誌與-run-記錄)）。collect 成功後跑指標批次（目標日傳給批次；analyze 失敗也跑）、新聞題材建議彙整與追蹤計畫更新（兩者都不依賴 analyze）；candidates 成功才跑 candidate_notes（LLM 說明，結果不影響 run 狀態，[日誌與 run 記錄](SCHEDULING.md#日誌與-run-記錄)）；collect 失敗時後續步驟記 `skipped`。每次執行寫一列 `schedule_runs`，trading_calendar、strategy_levels 與 candidate_notes 以外任一步驟失敗則該 run 為 `failed`；當日目標第一次兩市都回 no-data 記 `non_trading_unconfirmed`，下一次觸發再確認（[daily／news 工作的註冊與管理](platform/windows.md#dailynews-工作的註冊與管理)）；exit code 與狀態見 [日誌與 run 記錄](SCHEDULING.md#日誌與-run-記錄)。 |
| `python -m worker.cli job daily\|news\|us [--data-dir DIR] [--log-dir DIR] [--trigger …] [--date YYYY-MM-DD] [--force] [--claude-cli PATH] [--skip-news-llm] [--min-free-memory-gb N] [--time-limit-minutes N] [--log-retention-days N]` | 排程執行的入口（#313）：取該 job 的檔案鎖、起跑前檢查，再以子程序跑 `daily`、`news` 後接 `news-llm`，或 `us` 的 `index-bars us-collect`（#568），套單次上限（`us` 預設 20 分）並寫 `<data>/logs/<job>-YYYYMMDD.log`；exit code 是該 worker 的碼。`daily` 與 `us` 被 `low_memory`、`git_busy`、`already_running` 擋下時，以 `--skip-reason` 讓 worker 記一筆跳過的 run；`news` 只記日誌。不 pull、不執行 git，版本是 image 的 `STOCK_IMAGE_TAG`／`STOCK_GIT_HEAD`（#340）。行為、日誌與鎖見 [daily／news 工作的註冊與管理](platform/windows.md#dailynews-工作的註冊與管理)、[日誌與 run 記錄](SCHEDULING.md#日誌與-run-記錄)。`daily` 與 `index-bars us-collect` 的 `--skip-reason` 只給 job 用。 |

| `python -m worker.cli maintenance on\|off\|status [--reason TEXT] [--only-manual] [--data-dir DIR]` | 手動開關[維護模式](SCHEDULING.md#維護模式)（#468），只用在 RELEASE 的 `init-db`→`deploy.sh`：`on` 寫入 `<data>/locks/maintenance`，之後排程的 daily 與 news 只記 `skipped reason=maintenance`、不寫 DB，看門狗與 monitor 照常；`off` 刪掉它（`--only-manual` 只關手動開的、作業持有的不動，`deploy.sh` 用）；兩者都要 `--reason`，記在 `<data>/logs/maintenance.log`。輸出 JSON（狀態、開始時間、時數、原因、owner、心跳、`serve_running`、開著時的 `running_jobs`）；不寫 DB。`backfill`、`backtest`、`events backfill`、`fundamentals backfill`、`revenue backfill`、`instruments repair --apply` 不必手動開：起跑時自己持有維護模式、每分鐘心跳、結束時關掉；有 daily／news job 還在跑、另一個作業持有，或維護模式是手動開的（部署中）時拒絕起跑（exit 75）；執行中失去維護模式（逾時被解除、心跳寫不進去）就停下，exit 70。 |

## 資料品質與研究結果

- 逐用途檢查交易所、標的、日期與欄位；行情 success 不代表 chips、events、actions 完整。無資料、錯日與 incomparable 的判定見 [共通原則](../spec/README.md#共通原則)。
- entry、breakout、pullback、invalid、targets 是規則參考價，不是持倉成本、委託或成交；`cost_included=false` 只表示價位公式未扣成本。
- `data_cutoff`、`signal_date`、`earliest_execution_date`、naive `created_at` 都不能證明 `decision_at`。unknown time／basis 必須連同 reason 保留。
- `/api/ingestion-runs`、`/api/backfill-runs`、`/api/data-quality`、`/api/backtest/summary` 提供稽核摘要，`/api/coverage` 提供 coverage。`/api/ingestion-runs` 的列表預設不含各 run 的 `metadata`（官方 collect 一筆約 300 KB、最大 10 MB，一頁 50 筆曾達 24 MB），加 `include_metadata=true` 才回傳（[#462](https://github.com/YiCheng0608/stock-lab/issues/462)）。前端入口為 `/research/backtest`、`/research/coverage`、`/system/data-quality`。
- 產業分類 run 與 ordinary、ETF、新上市 receipt 分開讀，其中一個 success 不代表全分類已核實（[產業分類](../INDUSTRY_CLASSIFICATION.md)）。

| `python tools/verify/page_checks.py --api <API> --web <preview> --db <stock.db> --out <目錄> [--fixture] [--g7]` | 跑 `features/*.md` 標「CI」的全部檢查：抓 API、以 `screenshot.cjs` 截圖（4 個瀏覽器並行）、比對頁面文字與 API／`db_facts.py`；結果是通過／失敗／無法判定三態，並依規則抽好「人工」檢查的樣本（`manual/`）。`--fixture` 另比對 `EXPECTED`、對無資料的 9204 跑個股檢查，且無法判定也算失敗；`--g7`（V1 G7 窗口專用，已結束，見 [RELEASE 的 V1 發佈隔離（歷史）](../RELEASE.md#v1-發佈隔離歷史)）在有未 commit 改動或 HEAD 不等於 `origin/release/v1` 時拒跑。輸出 `summary.md`、`status.md`、`results.json`、`api/`、`shots/`、`manual/`，有失敗 exit 1（[已知失敗](../../.claude/skills/verify-stock-lab/features/README.md#已知失敗)除外），features 不一致或 `--g7` 不符 exit 2。preview 用 `tools/verify/vite.preview.mjs`（`VERIFY_DIST`、`VERIFY_WEB_PORT`、`VERIFY_API_URL`）。CI `verify` job 以假資料庫跑 `verify_plan.py` 選出的頁（每晚與手動觸發是五頁全套），結果與截圖上傳成 artifact `verify-<attempt>` |
| `python tools/research/backtest_research.py --db <副本 stock.db> --start YYYY-MM-DD --end YYYY-MM-DD [--ablate all\|<策略>:<條件> ...] [--regime all|<策略>:<濾網> ...] [--slim] [--no-canonical]\|<策略>:<濾網> ...] [--no-canonical] [--min-free-gb 10] [--force]` | 研究回測（[#318](https://github.com/YiCheng0608/stock-lab/issues/318)）：canonical 策略加上 `--ablate` 列出的 ablation（`app.strategies.ablation`，例如 `breakout_v3:group`）與 `--regime` 列出的大盤狀態濾網版本（`app.strategies.regime`，例如 `pullback_v4:r3`；[#546](https://github.com/YiCheng0608/stock-lab/issues/546)，重播前讀一次副本的 TAIEX 收盤，逐日指到該分數日）在同一次重播中評估，每檔每日的輸入只建一次。每列訊號都記錄 registry 全部策略的狀態，列大小隨策略數成長：12 個策略每列約 6.2 KB、重播約 93 秒／日（2026-11-08 實測）。`--slim` 在每個分數日的訊號 flush 前，把該 run 不可行動的列（`observation`／`data_incomplete`／`invalid_levels`）的 `rule_evidence_json` 縮成 `actionable: false`、策略名與版本、自己策略的 state／reasons，`rationale` 清空；狀態、價位、追蹤與 settlement 不變（追蹤對這些列只讀 `actionable`），12 策略 3 日由約 600 MB 降到約 62 MB、約 65 秒／日。會寫入 `--db`（signals、settlements、`run_type=backtest` 的 run），所以只對 `copy_db.py` 的副本跑。`--db` 在 `stock-lab-data` 或 `STOCK_DATA_DIR` 內、與正式 `stock.db` 是同一個檔案（含 hard link，以 `os.path.samefile` 比對）、台北 21:30～23:30（daily 與 23:00 的重試，#466）、或可用實體記憶體低於 `--min-free-gb` 時，不載入程式直接 exit 2。重播中每個交易日與每批追蹤 commit 後再查一次時段，進入 18:30 就停下，run 記 `failed`（`BacktestPaused`），exit 3 並在 `rerun` 印出接續的命令（同樣參數、不帶 `--force`）。重跑從頭重播，已 commit 的列覆寫成相同結果，所以起跑時間加預估耗時（12 個月約 5.4 小時）最好不跨進 21:30。印出 run、registry、migration 與重播秒數、峰值 working set、WAL 最大值（每 5 秒取樣），以及各策略的訊號、狀態與 settlement 數 |
